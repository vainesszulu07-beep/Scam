Partner API Integration Guide

Technical documentation for developers and IT technicians integrating their applications with ZambianAdvertisements.

1. System overview

ZambianAdvertisements provides an application authentication system. A partner application must first authenticate its credentials with our backend before it can obtain an authentication token for advertising requests.

01. Partner Backend Stores the assigned credentials securely.
02. Verification Request Sends the required credentials to our API.
03. Authentication Our backend checks the application credentials.
04. Token Issued A successful authentication returns a token ID.
05. Ad Request The frontend uses the returned token ID and Sub ID.

2. Verification endpoint

Your backend must send a POST request to the following ZambianAdvertisements endpoint.

https://scam-gamma.vercel.app/api/verify-partner.js

HTTP method: POST

Content-Type: application/json

Request format: JSON

Authentication requests must be made from your backend server, not directly from your frontend. Your secret key must never be exposed in browser JavaScript.

3. Credentials supplied to your application

Each approved partner application receives the following credentials from ZambianAdvertisements.

Credential What it identifies Expected format Request field
Sub ID Your registered partner application identifier. 8 uppercase hexadecimal characters. subid
Application ID The unique application ID assigned to your app. UUID format. id
Secret Key Your private authentication credential. Non-empty secret string. secret_key
Never publish your secret key, share it in frontend code, or include its actual value in public documentation. Only authorised server-side code should access it.

4. Configure your environment variables

Your backend can read credentials using specific environment variable names. These names must be entered exactly as shown. Do not rename them.

Required environment variable names

Environment variable name Value to insert
AD_NETWORK_VERIFY_URL The ZambianAdvertisements verification endpoint.
PARTNER_SUBID Your assigned Sub ID.
PARTNER_APP_ID Your assigned Application ID.
PARTNER_SECRET_KEY Your assigned Secret Key.

Environment variable configuration example

This example shows the exact naming structure. Replace the placeholder values with the credentials supplied to your application.

Backend environment configuration 
AD_NETWORK_VERIFY_URL=https://scam-gamma.vercel.app/api/verify-partner.js
PARTNER_SUBID=YOUR_ASSIGNED_SUBID
PARTNER_APP_ID=YOUR_ASSIGNED_APP_ID
PARTNER_SECRET_KEY=YOUR_ASSIGNED_SECRET_KEY
Where to enter these: Open your backend hosting provider's project settings, locate Environment Variables, and create each variable using the exact name above and its corresponding value.
These values belong on your backend server. Do not place them in HTML, frontend JavaScript, public GitHub repositories, or publicly accessible configuration files. Environment variables are recommended, but they are not the only way to configure your backend. See Section 6 for the alternative without environment variables.

5. Credential-to-request mapping

Your backend environment variable names and the JSON fields sent to our API are different. Your backend must map them correctly.

Exact mapping expected by our backend 
const payload = {
  subid: process.env.PARTNER_SUBID,
  id: process.env.PARTNER_APP_ID,
  secret_key: process.env.PARTNER_SECRET_KEY
};

Our backend expects the JSON properties to be exactly subid, id, and secret_key.

Do not send PARTNER_SUBID, PARTNER_APP_ID, or PARTNER_SECRET_KEY as JSON property names. Those are environment variable names, not request field names.

6. Exact authentication request

Your backend must send a POST request containing the three credentials in a JSON request body.

Request URL

https://scam-gamma.vercel.app/api/verify-partner.js

Request headers

HTTP headers 
Content-Type: application/json
X-Request-ID: A-UNIQUE-REQUEST-ID

Exact JSON request body

Request body 
{
  "subid": "YOUR_ASSIGNED_SUBID",
  "id": "YOUR_ASSIGNED_APP_ID",
  "secret_key": "YOUR_ASSIGNED_SECRET_KEY"
}

Replace the placeholders with the actual credentials assigned to your application. The names of the JSON properties must remain unchanged.

Method A: Using environment variables

This method reads your credentials from your backend environment variables. It is the recommended approach.

Server-side JavaScript request using environment variables 
import crypto from "node:crypto";

const requestId = crypto.randomUUID();

const response = await fetch(
  process.env.AD_NETWORK_VERIFY_URL,
  {
    method: "POST",
    headers: {
      "Content-Type": "application/json",
      "X-Request-ID": requestId
    },
    body: JSON.stringify({
      subid: process.env.PARTNER_SUBID,
      id: process.env.PARTNER_APP_ID,
      secret_key: process.env.PARTNER_SECRET_KEY
    })
  }
);

const result = await response.json();

if (
  !response.ok ||
  result.success !== true ||
  result.authorized !== true
) {
  throw new Error(
    result.message || "Partner authentication failed"
  );
}

// Authentication successful.
const subid = result.subid;
const token_id = result.token_id;

console.log("Partner authenticated successfully.");

Method B: Without environment variables

This alternative sends the same request but places the assigned credentials directly in your backend code. You do not need to configure the four environment variables listed in Section 4 when using this method.

Server-side JavaScript request without environment variables 
import crypto from "node:crypto";

// Your assigned credentials.
// Replace these placeholders with your actual credentials.

const SUBID = "YOUR_ASSIGNED_SUBID";
const APP_ID = "YOUR_ASSIGNED_APP_ID";
const SECRET_KEY = "YOUR_ASSIGNED_SECRET_KEY";

const VERIFY_URL =
  "https://scam-gamma.vercel.app/api/verify-partner.js";

// Generate a unique request ID.
const requestId = crypto.randomUUID();

// Send the authentication request.
const response = await fetch(VERIFY_URL, {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    "X-Request-ID": requestId
  },
  body: JSON.stringify({
    subid: SUBID,
    id: APP_ID,
    secret_key: SECRET_KEY
  })
});

// Read the response.
const result = await response.json();

// Check authentication.
if (
  !response.ok ||
  result.success !== true ||
  result.authorized !== true
) {
  throw new Error(
    result.message || "Partner authentication failed"
  );
}

// Authentication successful.
const subid = result.subid;
const token_id = result.token_id;

console.log("Partner authenticated successfully.");
Important distinction: Both methods send exactly the same JSON request to the same endpoint. The only difference is where your backend obtains the credentials. Method A reads the values from environment variables. Method B reads the values from constants in your backend code.
Method B must only be used in private server-side code. Never place these credentials in frontend JavaScript, HTML, mobile application source code, or a public GitHub repository. Anyone who can access exposed source code may be able to obtain your Secret Key. Environment variables are the recommended method for protecting credentials.
Generate a new unique Request ID for each authentication request. This helps both systems identify and investigate individual requests.

7. Successful authentication response

When the credentials are correct, the ZambianAdvertisements backend returns HTTP status 200 with a JSON response similar to the following.

SUCCESS RESPONSE · HTTP 200
Example response 
{
  "success": true,
  "authorized": true,
  "message": "Partner verified",
  "subid": "YOUR_ASSIGNED_SUBID",
  "token_id": "<TOKEN_RETURNED_BY_BACKEND>",
  "session_id": "<SESSION_ID_RETURNED_BY_BACKEND>",
  "diagnostics": {
    "request_received": true,
    "body_valid": true,
    "supabase_configured": true,
    "database_connected": true,
    "record_found": true,
    "secret_match": true,
    "token_generated": true,
    "token_saved": true,
    "failed_stage": null
  },
  "request_id": "<REQUEST_ID>"
}

What the response means

success: The authentication request was processed successfully.

authorized: The supplied application credentials were verified.

subid: Your registered Sub ID, returned by our backend.

token_id: The authentication token generated and saved by our backend. This is required for subsequent advertising requests.

session_id: The database session record associated with the generated token.

diagnostics: Indicates which authentication operations were completed successfully.

request_id: The unique identifier used to trace the authentication request.

8. Response received by your sender backend

If you use the provided sender-backend integration, it forwards the partner response and adds a sender_diagnostics object.

Additional sender diagnostics 
{
  "sender_diagnostics": {
    "request_id": "<REQUEST_ID>",
    "environment_configured": true,
    "request_sent": true,
    "response_received": true,
    "upstream_status": 200
  }
}

The complete forwarded response contains the original authentication response fields as well as this additional sender_diagnostics object.

9. Using the token for advertising requests

After successful authentication, your backend receives two important values:

token_id The authentication token returned by our backend.
subid Your registered partner application identifier.

These two values are subsequently used by your frontend when requesting an advertisement through your advertising integration.

Example of the two values

Advertising request credentials 
{
  "subid": "<SUBID_RECEIVED_FROM_BACKEND>",
  "token_id": "<TOKEN_ID_RECEIVED_FROM_BACKEND>"
}
One-time token rule: A token is intended to expire after it has been used. Do not reuse the same token for another advertising request after it has been consumed. Obtain a fresh token through authentication when a new token is required.
The token ID is a sensitive authentication value. Do not publish it, place it in public logs, or share it with unrelated applications. Use HTTPS when transmitting it. Never send your Secret Key to the frontend.

The frontend should receive only the values needed for the advertising integration. Your Application ID and Secret Key must remain on your backend.

10. Possible authentication errors

If authentication fails, our backend responds with an appropriate HTTP status and diagnostic information.

HTTP status Possible stage Meaning
400 input_validation / body_inspection Invalid JSON or missing/invalid credentials.
401 database_lookup / secret_key_comparison Application was not found or the secret key did not match.
405 method_check The request must use POST.
500 supabase_environment_check / database operations Server configuration or internal database problem.
502 network_request / response_parsing The sender could not obtain a valid response from the partner backend.

Example error response

Invalid credentials 
{
  "success": false,
  "authorized": false,
  "stage": "input_validation",
  "message": "Required credentials are missing or invalid",
  "invalid_fields": [
    "subid"
  ],
  "received": {
    "subid": false,
    "id": true,
    "secret_key": true
  },
  "request_id": "<REQUEST_ID>"
}

Check the stage, message, invalid_fields, and request_id when troubleshooting authentication failures.

11. Security requirements

All integration partners are expected to follow these requirements:

1. Store all assigned credentials in secure backend-only configuration. Environment variables are recommended.

2. When using environment variables, use the exact variable names documented above.

3. Send authentication requests using POST and JSON.

4. Keep the Secret Key exclusively on your backend.

5. Do not reuse an authentication token after it has been consumed.

6. Use HTTPS for communication.

7. Do not expose authentication tokens or Secret Keys in public logs.
The exact advertising request endpoint and its complete request contract should be obtained from the advertising integration documentation. The two credential fields above identify the values to use; they do not define an additional endpoint.

12. Integration checklist

Before considering your integration complete, check that:

□ The four environment variables have been configured, or the credentials have been securely configured directly in private backend code.

□ The verification URL is correct.

□ The POST request uses the correct JSON property names.

□ Your backend can receive and parse the JSON response.

□ Your application checks both success and authorized.

□ Your application can securely handle the returned token_id and subid.

□ Your advertising integration handles tokens as one-time-use credentials.
